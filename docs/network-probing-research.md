# 网络探测：业界做法与本次实测

> 本文回答两个问题：
> 1. 业界成熟的连通性探测是怎么做的？
> 2. 2026-11-11/12 实测的这张校园网，到底是什么状态？
>
> **本文的实测结论推翻了本仓库此前两轮的错误判断**，请以本文为准。

## 第一部分：业界成熟做法

### 1.1 标准：RFC 8908 Captive Portal API

IETF 的标准做法（Apple、Google、Microsoft 都遵循）是三层判定：

| 层 | 手段 | 判据 |
|---|---|---|
| 链路 | 有无 IPv4/IPv6 地址 | 没地址 = 链路层失败 |
| 网络 | ICMP / DNS / TCP 到网关 | 网关不通 = 本段网络问题 |
| 服务 | HTTP 探测 + **预期响应比对** | 响应与预期不符 = 被劫持/门户 |

关键点：**不能只看「有没有响应」，要看「响应是不是预期的」**。

### 1.2 Apple 的 Captive Network Assistant（CNA）

macOS/iOS 的判定流程：

1. 请求 `http://captive.apple.com/hotspot-detect.html`
2. 期望返回**精确内容** `<HTML><HEAD><TITLE>Success</TITLE></HEAD><BODY>Success</BODY></HTML>`
3. 如果返回 302 / 内容不同 → 判定为 captive portal，弹登录窗

**教训**：Apple 用的是「内容精确匹配」，不是「状态码 200 就算通」。
这正是本仓库 `cnHome` 那个错误改动的问题——百度返回 200，但内容不是预期的，
却被当成了门户拦截。

### 1.3 Google 的 connectivitycheck

`http://connectivitycheck.gstatic.com/generate_204`

- 期望 **HTTP 204 且响应体为空**
- 返回 200 / 302 / 有内容 → 被劫持
- 这是最广泛采用的方案，因为它：
  - 响应体为 0，最省流量
  - 204 语义明确（无内容）
  - 全球 anycast，延迟低

### 1.4 Microsoft NCSI

`http://www.msftconnecttest.com/connecttest.txt`

- 期望返回**精确文本** `Microsoft Connect Test`
- 内容不符 → 判定被劫持

### 1.5 三层探针的工业实践

成熟客户端（如 Firefox、Chrome、Windows NLA）普遍采用：

```
L1 链路层：有 IP 地址？默认路由存在？
L2 网络层：DNS 能解析？网关能 ping？
L3 应用层：HTTP 探测返回预期内容？
```

**逐层降级**：L1 失败就没必要测 L3；L2 失败说明是本段网络问题，
不是运营商/防火墙问题。

### 1.6 关于「加密通道」的探测

业界**没有**用「发 ClientHello 看有没有回包」作为标准探测手段，原因：

1. 干扰正常 TLS 握手，可能触发服务端风控
2. 难以区分「TLS 被切断」和「这个 IP 本身不可达」
3. 结果不稳定（GitHub 这类站点本身有间歇性）

**但作为诊断工具它是有效的**——前提是配合「多目标 + 多次采样」，
且**必须用 `IP_BOUND_IF` 绑定物理网卡**。

## 第二部分：本次实测（2026-11-11/12，JLU.WIFI）

### 2.1 测量方法（这是最容易出错的地方）

**必须用 `IP_BOUND_IF`，不能用 `curl --interface` 或 `nc -s`。**

原因：本机路由表被代理改成了「路由分裂」：

```
1        → utun4
2/7      → utun4
4/6      → utun4
8/5      → utun4
10       → en0（校园网段例外）
default  → utun4
```

`1`、`2/7`、`4/6`、`8/5` 这四条加起来**覆盖整个 IPv4 空间**，比 `default`
更精确。所以：

- `curl --interface en0`：只改**源地址**，路由查找仍按目的地址 → **进 utun4**
- `nc -s <本机 IP>`：同上 → **进 utun4**
- `IP_BOUND_IF`（socket 选项）：内核级绑定出口网卡 → **真绕开**

**这是前两轮结论错误的根本原因。** 我用前两种方法测出的「境外全挂」，
测的其实是代理路径。

### 2.2 权威测量结果

`IP_BOUND_IF` 绑 en0，每目标采样 6 次，443 端口：

| 目标 | 结果 | 稳定性 |
|---|---|---|
| github.com | 通 | **6/6 稳定** |
| github-pages | 通 | **6/6 稳定** |
| fastly | 通 | **6/6 稳定** |
| baidu | 通 | **6/6 稳定** |
| qq | 通 | **6/6 稳定** |
| cloudflare-dns (1.1.1.1) | 不通 | **0/6 稳定** |

80 端口补充：
- `1.1.1.1:80` 通、`1.1.1.1:443` 不通（同一 IP 端口分裂）
- `8.8.8.8` 80/443 全不通
- `104.16.132.229`（Cloudflare）80/443 全不通

### 2.3 代理路径对照

走 `socks5h://127.0.0.1:1082`，每目标 4 次：

| 目标 | 结果 |
|---|---|
| www.baidu.com | 4/4 通 |
| www.qq.com | 4/4 通 |
| www.cloudflare.com | **0/4** |
| en.wikipedia.org | **0/4** |
| www.python.org | **0/4** |

### 2.4 代理的实际连接（决定性证据）

`lsof` 看代理进程的 TCP 连接，**全部指向国内地址**（此处已脱敏）：

```
<国内 A>:443   <国内 B>:443   <国内 C>:443
<国内 D>:443   <国内 E>:443   <国内 F>:443
<国内 G>:443   <国内 H>:443   <国内 I>:443
```

**没有任何一条连接到境外节点。**

UDP 侧只有两条 443：一条是**校园网出口**（直连可达），一条是
**代理出口**（直连超时）。两个出口指向完全不同的路径。

### 2.5 由此得到的结论

**代理的境外出口没有建立起来。**

- 国内流量：走直连，正常
- 境外流量：代理试图转发，但没有可用的境外节点 → 全部失败
- 校园网直连境外：**部分可达**（GitHub、Fastly 稳定通）

所以用户看到的「境外全挂」，原因是**代理节点侧**，不是校园网封锁。

### 2.6 必须纠正的两个此前结论

| 此前结论 | 实际情况 | 错在哪 |
|---|---|---|
| 「校园网封锁了所有出境 443 TLS」 | GitHub/Fastly 6/6 稳定通 | 测量走了 TUN，测的是代理 |
| 「GitHub 直连通、代理不通 → 代理有问题」 | GitHub 有间歇性，不能作判据 | 用单一不稳定目标下结论 |

第二条是用户直接纠正的，值得记下来：**判据必须选稳定的目标**。

## 第三部分：对 JLU Gate 的建议

### 3.1 探针应该怎么改（1.5.0 已做 + 待做）

**已做（`5751fcd`）**：
- 加 L3 TLS 层探测，多目标、必须全部被切断才报 `tlsBlocked`
- 结论类型区分 `healthy` / `captivePortal` / `tlsBlocked` / `unreachable`

**已修（`832dcb7` + `812c6c9`）**：
- DNS 多结果降级：原来只取第一个成功的解析结果，一旦那个 IP 不可达就误判断网
- 默认 DNS 改成校内优先：原来 `[1.1.1.1, 8.8.8.8]`，实测 `8.8.8.8` 完全不通、
  `1.1.1.1` 会解析到境外不可达 IP

**待做**：
1. **必须做内容比对，不能只看状态码**：参照 Apple CNA / Microsoft NCSI。
   `generate_204` 要校验「204 且响应体为空」。
   实测证据：同一个 IP（国内 CDN 节点）请求 `generate_204` 返回 204，
   但请求 `google.com` 返回 404——**204 只能证明「能连到一个 HTTP 服务」，
   不能证明「能访问境外真实服务」**。这正是 `PLAN.md:107` 写明、但代码
   还没落实的那条。
2. **探测必须走 `IP_BOUND_IF`**：`ReachabilityService` 用 `URLSession`，
   测的是代理路径（见 §4）。

### 3.2 诊断文案要区分「两种不通」

这是本次最大的产品教训：

| 现象 | 用户以为 | 实际 |
|---|---|---|
| 国内通、境外不通 | 「校园网封了」 | 可能是代理节点挂了 |
| 境外直连通、代理不通 | 「网坏了」 | 代理配置/节点问题 |

**JLU Gate 应该明确告诉用户：「你的校园网是通的，问题在代理」。**
这句话能省掉大量排查时间——本次排查绕了三轮弯路，就是因为没有这句话。

### 3.3 不建议做的事

- **不要**用「单次 TLS 握手失败」判定网络故障：GitHub 这类站点本身
  有间歇性，单次结果不可靠
- **不要**用 `URLSession` 做需要绑定网卡的探测（`PLAN.md:22` 已禁止）
- **不要**把 `generate_204` 返回 204 当成「一切正常」的唯一依据

## 第四部分：`ReachabilityService` 的问题

`Sources/JLUGateNet/ReachabilityService.swift` 用 `URLSession` 探测，
**无法绑定出口网卡**，违反 `PLAN.md:22`。

实测矛盾（同一时刻、同一台机器）：

| 命令 | 探测方式 | 结论 |
|---|---|---|
| `--portal-check` | `IP_BOUND_IF` 绑 en0 | 「已在线」 |
| `--reach` | `URLSession`（走 TUN） | 「国外网站全都打不开」 |

`--reach` 测的是**代理路径**。所以「诊断」页那张站点表，在有代理时
反映的是**代理状态**，不是校园网状态。

**建议**：要么改成 `IP_BOUND_IF`，要么在 UI 上明确标注「这是经代理的
结果」。不要让它继续误导排查——本次排查就被它误导过。
