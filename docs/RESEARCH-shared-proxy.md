# 研究：让共享出去的热点流量也走代理

> 结论先说：**可行，而且不需要代理软件配合。**
> 我们用一个自己控制的透明转发器，按 TLS 的 SNI / HTTP 的 Host 决定把流量交给谁——完全绕开 TUN 对"转发包"的处理。

日期：2026-11-03 · 状态：PoC 已验证

---

## 1. 问题

用户实测：小火箭开 TUN 后开热点，客户端能上网，但**流量没走代理**。

这不是配置错误，是多数 TUN 实现的通病：

1. 代理从 utun 读包后，靠**源地址/端口**去对应本机进程；转发来的包源地址是 `192.168.50.x`，本机没有这个 socket → 落入"未知流量"分支；
2. 即便处理了，回包要写回 utun 再让内核转发回客户端，很多实现只做了"本机收包"这条路径；
3. pf 规则/路由常按 uid 或"本机"写死，转发的包不满足条件。

**所以不能指望代理软件；要么换软件，要么我们在更底层补一层。**

---

## 2. macOS 到底提供了什么（实测）

| 原语 | 是否可用 | 说明 |
|---|---|---|
| `/dev/pf` | ✅ 存在（`crw------- root:wheel`） | 但 **SDK 里没有 `net/pfvar.h`**，`DIOCNATLOOK` 这些 ioctl 的 ABI 要自己声明，跨系统版本有风险 |
| `pfctl` | ✅ `/sbin/pfctl` | 可下 `rdr` / `nat` 规则，需要 root |
| `SO_ORIGINAL_DST` | ❌ Darwin 没有 | Linux 透明代理的标准做法在 macOS 上不成立 |
| divert 套接字 | ⚠️ 不确定 | 头文件不全，社区用法罕见 |

**结论：不要走"查 NAT 表拿原始目的地"这条路。** 改用**协议层信息**推导目标——TLS 握手里的 SNI、HTTP 里的 Host。这两样客户端一定会带，而且和 DNS、fake-ip 都无关。

## 3. PoC 与实测结果

代码在 `Tools/research/`：

- `sni_relay_poc.py`：监听本地端口，读客户端首个 TLS ClientHello，解析 SNI，然后直连或用上游 HTTP 代理 `CONNECT` 转发；
- `mini_connect_proxy.py`：一个 20 行的 HTTP CONNECT 代理，仅用于测试链路。

实测（本机，2026-11-03）：

```text
# 直连模式
[relay] listening 127.0.0.1:8443 upstream=direct
[relay] SNI='example.com' 首包=321B
curl → HTTP 200

# 经上游代理（CONNECT）
[relay] SNI='example.com'
[proxy] CONNECT example.com:443
curl → HTTP 200
```

**两条路都通**：SNI 解析正确、字节流双向透传、HTTPS 端到端成功。

### 3.1 关键验证：直接交给本机真实代理（2026-11-03）

本机 `127.0.0.1:1082` 是一个 mixed 端口（HTTP CONNECT 与 SOCKS5 都可用，实测均返回 200）。
把 relay 的上游指向它之后：

```text
[relay] SNI='example.com'      → HTTP 200
[relay] SNI='www.google.com'   → HTTP 204
```

**这就是“同等效果”的技术支点**：relay 用**域名**向本机代理发起 `CONNECT`，
代理软件按自己的规则决定直连还是走隧道——规则、分流、订阅，全部原样生效，
客户端那台机器什么都不用配、也什么都不用装。

## 3.5 为什么这个方案没有"隧道悖论"

用户的判断是对的：**只要指望 TUN 去处理转发包，就是死路**——
隧道全量劫持后，转发包的源地址是客户端，代理无法把它对应到任何本机 socket，回包也回不去。
"两全其美"（既全量劫持、又让共享设备也能走）在 TUN 这一层确实不存在。

差别在于**截获点**：

| | TUN 方案（失败） | pf rdr 方案（本方案） |
|---|---|---|
| 截获时机 | 路由查找**之后**，包已经决定进 utun | 路由查找**之前**，在 `bridge100` 入口就改目的地 |
| 截获者 | 代理软件的 TUN 栈 | 内核 pf |
| 后续 | 代理要知道"这个包从哪来、回给谁" | 包变成**本机到 127.0.0.1 的连接**，由我们的 relay 承接 |
| 与 TUN 的关系 | 依赖 TUN 支持转发 | **完全无关**：relay 是普通本机进程 |

关键一句：**relay 连的是 `127.0.0.1:<代理端口>`，走的是环回，TUN 根本不会碰它。**
代理看到的是"本机某个进程要访问 example.com"，于是照常执行规则、照常走隧道。

所以不是"两全其美"，而是**换了一个不冲突的分工**：
TUN 继续只管本机；客户端流量由 pf + relay 走另一条路，最后在代理的本地端口汇合。

**唯一需要真机确认的**：pf 的规则顺序。macOS 的互联网共享自己也会往 pf 里塞 anchor，
我们的 `rdr` 必须排在它的 `nat` 之前，否则包会先被 NAT 掉。验证方法见 §1.1。

## 4. 完整链路（要落进产品时）

```text
客户端(192.168.50.x)
   │  TCP 443
   ▼
bridge100 ──pf rdr──► 127.0.0.1:8443   ← 只重定向 TCP，UDP 另有处理
   │
   ▼
sni-relay（我们自己的进程，随 App 起）
   │ 读 ClientHello → SNI
   ▼
上游代理（HTTP CONNECT / SOCKS5）
   │
   ▼
互联网
```

要点：

- **pf 规则**：`rdr pass on bridge100 inet proto tcp from 192.168.50.0/24 to any port {80,443} -> 127.0.0.1 port 8443`；
- **relay 进程**：跑在 helper 或主 App 的独立线程里，只监听 `127.0.0.1`，不接受外部连接；
- **上游**：用户填 `host:port`（或从系统代理设置读），relay 只用它做 `CONNECT`，不关心它内部怎么翻墙；
- **端口 80**：同样口径，读 `Host:` 头即可。

## 5. 边界（必须写进文档，不然会变成 bug 报告）

| 场景 | 行为 | 处理 |
|---|---|---|
| **HTTP/3 (QUIC, UDP 443)** | 绕过 pf 的 TCP 重定向，直连出去 | 在 bridge 上**丢弃 UDP 443**，强制客户端回落 TCP；或明确告知"视频类可能没走代理" |
| **ECH / ESNI（加密 SNI）** | 看不到 SNI | 回落：无法定目标 → 直连或拒绝（可配置） |
| 非 443/80 的 TLS | 不在重定向范围 | 可扩大端口集合，但每加一个就多一份风险 |
| 非 TLS、非 HTTP 协议 | 无法推导目标 | 直连（默认）或阻断 |
| 客户端走 DNS-over-HTTPS | 不影响：我们只看 SNI | — |
| 证书校验 | **不受影响**：我们只搬运字节流，不做 MITM | — |

## 6. 与产品的集成

| 项 | 设计 |
|---|---|
| 触发 | 只在「共享给其他设备 → 流量走代理」开启时启动 relay，关闭即停 |
| 权限 | pf 规则要 root → 由 §6.6 的最小特权 helper 代劳；relay 本身不需要 root |
| 上限 | 与 §15.8 一致：6 台 |
| 上游 | 默认读系统代理设置；读不到就要求用户填一个 `host:port` |
| 日志 | 只记 `SNI / 目标端口 / 命中规则`，**不记内容**；可一键清空 |
| 失败处理 | 上游不通 → 明确报错并**回落直连**（可选），不能让客户端"看起来联网但什么都不通" |

---

## 7. 风险与合规

- 只服务**同一用户自己的设备**，不做公开代理；
- 不修改、不注入用户的代理软件；
- 不解析、不改写 TLS 内容（纯字节流透传），不触碰证书；
- 平台规则上仍属"共享上网"，由使用者承担；产品不宣传该能力。
