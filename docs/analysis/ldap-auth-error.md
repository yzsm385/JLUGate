# 「ldap auth error」到底是什么问题（调研记录）

> 触发：真机连续登录失败，服务器原始原因串为 `ldap auth error`。
> 用户明确表示密码输入正确。本文只做取证与推理，不含猜测性结论。
> 具体账号、密码与摘要见 `local/PRIVATE.md`（本地私有，不入库）。

## 结论先行

**`ldap auth error` 不能等同于"密码错"。** 我们有硬证据：一次登录被服务器拒绝，
而这一帧的摘要与**真实密码**完全吻合（复算结果逐字节一致）。

## 证据 A：被拒的那一帧，用的就是正确密码

从 `local/PRIVATE.md` §4 取"第一次（失败）"的登录帧：

- 帧内摘要 A（0x04..0x13）：记为 `D_frame`；
- 用记录的真实密码复算：`MD5(0x03 ‖ 0x01 ‖ salt ‖ password)` → 记为 `D_calc`；
- **`D_frame == D_calc`**（16 字节完全一致）。

也就是说：这一次客户端的摘要是对的，服务器仍然回了 `ldap auth error`。
所以它的含义至少包含"账号当前状态不允许这次登录"，而不只是"密码错"。

## 证据 B：成功那一帧的摘要，用笔记里的 salt+密码复现不出来

"第二次（成功）"帧的摘要，穷举 90+ 种组合仍不匹配：

| 变量 | 试过的取值 |
|---|---|
| 前缀 | `03 01` / `03` / `01` / `03 01 00 1f` / `1f 03` |
| salt | 抓包里记录的三个 salt（`49cb…`、`6ecb…`、`14cb…`），以及各自的字节反序 |
| 其它拼装 | `salt+密码`、`03 01 salt 密码 mac`、`+hostname`、`账号+salt+密码`、UTF-16LE 密码 |

只有**失败帧**命中。结论：成功那次用的 salt（或密码）与笔记里记录的不一致，
**不能用它当"我们的算法对不对"的对照组**。

## 证据 C：失败发生时，账号很可能仍在线

用户提供的诊断文件（2026-11-04T09-39-58Z）时间线：

```
09:16:29  passive watch: 已在线上，状态置为已连接
09:18:10  passive watch: en7 -> healthy
…（约每 50 秒在 healthy / unreachable 之间抖动）…
09:32:32  passive watch: 已在线上，状态置为已连接
09:36:42  打开向导
09:37:28  localPortInUse(61440)          ← 端口被占（另一份 App 或官方后台）
09:39:08  challenge 应答（salt 取自应答 0x04..0x08）  ← 链路正常
09:39:09  登录被拒：ldap auth error      ← 连续三次都是这个
```

关键点：**在登录尝试之前，账号已经处于"在线"状态**（被动观测一直 healthy）。
JLU 的 Dr.Com 网关对"同账号二次登录"经常回一个通用失败串，而不是明确的"已在别处登录"。

另一佐证来自抓包：同一次会话里**第一次登录失败（ldap auth error）、几分钟后第二次成功**——
与"会话未释放，稍后自然可登"的行为一致。

## 可能原因排序

| # | 假设 | 支持证据 | 如何验证 |
|---|---|---|---|
| 1 | **账号会话未释放**（服务器还认为你在线上） | 诊断日志在尝试前一直"已在线上"；抓包里有"先失败后成功"的先例 | 等 1–5 分钟 / 让上一台设备退出后再试 |
| 2 | **我们的登录包与官方客户端有差异**（校验字段） | 与成功帧逐字节对比有 7 段差异：`0x03a..0x04f`(22B)、`0x057..0x058`、`0x061..0x068`、`0x13a..0x143`、`0x146..0x149`、`0x154..0x155`、`0x004..0x013`(摘要) | 需要官方客户端的完整 pcap，逐字段判定哪些是随机、哪些是校验 |
| 3 | 密码/账号确实不对 | 用户否认；且证据 A 显示正确密码也会被拒 | 用网页版（mails / 自助平台）登录同一套凭据 |
| 4 | 服务器限流/维护 | 无直接证据 | 换时间段再试 |

## 下一步需要的一份材料

`~/Desktop/login-full.pcap`（2026-11-02 20:29–20:31 抓的）。它可以一次性回答三件事：

1. 每次登录用的 **salt** 到底是哪 4 个字节 → 验证我们的 `0x04..0x08` 解析；
2. 官方客户端的 342 字节登录包与我们**逐字节**差在哪 → 找出 7 段差异里哪些是必需的校验；
3. 失败那次是否也用了正确密码（复算摘要即可）。

工具已就绪（不含密码、可打码输出）：

```bash
python3 Tools/analysis/verify_login_pcap.py ~/Desktop/login-full.pcap \
        --password '你的邮箱密码' --redact
```

输出示例（合成数据）：

```
[1700000000.000] 挑战应答 serial=0x1d63 salt=49cb720f
[1700000001.000] 登录包 #1 账号=hua*** MAC=9c:*** salt=49cb720f 摘要=✅ 匹配
```

## 处理方式的调整（不再甩锅密码）

- 界面不再说"密码不对"，改为："服务器回 `ldap auth error`——常见原因：账号在别处在线、服务器忙，或密码需重输"；
- 收到该错误时**自动换新 salt 重试 2 次**（同一密码也常常第二次就过）；
- 不再自动清除已保存的密码；
- 保留「重新输入密码」按钮，但由用户决定是否重输。
