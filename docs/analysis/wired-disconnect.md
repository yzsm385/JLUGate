# 有线网「十几分钟断一次」的真实原因（2026-11-07）

> 证据：`docs/debug_proof/` 里 11-04 至 11-07 的 7 份真机诊断 + 官方客户端抓包
> （`docs/protocol-findings.md` §7 的 40/40 报文）。
> 结论：**保活 B 的 0x05 字段被当成了「序号」，它其实是「包类型」**。

## 1. 现象：不是掉线，是每 10～14 分钟被强制重登一次

把诊断里 `状态：idle → discovering` 的时间点排一下（全部是有线 en7、全部 login 成功）：

| 诊断文件 | 登录时刻 | 与上一次的间隔 |
|---|---|---|
| 2026-11-05T13-06-47Z | 12:54:12 / 13:06:04 | 11m52s |
| 2026-11-05T13-26-45Z | 13:13:28 | 7m24s |
| 2026-11-05T13-41-31Z | 13:27:44 | 14m16s |
| 2026-11-05T13-42-51Z | 13:41:42 | 13m58s |
| 2026-11-06T03-44-17Z | 03:32:55 / 03:43:32 | 10m37s（接着 12s 后又登一次） |
| 2026-11-07T02-29-42Z | 02:18:14 / 02:29:11 | 10m57s |
| 2026-11-07T03-49-16Z | 03:14:11 / 03:26:03 / 03:38:00 | 11m52s、11m57s |

每次都「重登成功、状态回 online」，所以用户看到的是「网每隔十几分钟断一下」，
而不是彻底连不上。7 份诊断、跨 4 个版本（1.3.3 → 1.4.2）都是这个节奏。

同期的两个伴随症状：

1. `保活B 超时（累计 21 次）`——**整场只有前两包有应答**；
2. `保活A 应答 在线=…s` 一直在回，但 A 的统计在会话末期才停（重登前 1～2 分钟），
   说明是**服务端主动释放了会话**，不是本机网络断。

## 2. 根因：0x05 是包类型，不是「请求/应答共用的序号」

官方抓包里的一对 B 保活（`docs/protocol-findings.md` §7）：

```
请求 07 05 28 00 0b 01 dc 02 …   → 0x05 = 01
应答 07 05 28 00 0b 02 dc 02 …   → 0x05 = 02
请求 07 05 28 00 0b 03 dc 02 …   → 0x05 = 03
应答 07 05 28 00 0b 04 dc 02 …   → 0x05 = 04
```

1.4.1 把这一列读成「请求/应答共用的自增序号」，于是发成 `01 / 03 / 05 / 07 …`。
但按吉林大学仍在维护的社区实现
[jlu-drcom-ng v2.0.0](https://github.com/hZsFN/jlu-drcom-ng)（`drcom/protocol.py`
的 `build_keepalive2_packet`）与 drcom-generic 的约定：

| 偏移 | 含义 | 取值 |
|---|---|---|
| `0x01` | 计数器 | 每发一个 B 包 +1（05、06、07…） |
| `0x05` | **包类型** | `01` = A 包，`03` = C 包；应答 = 类型 + 1（`02`、`04`） |
| `0x06–0x07` | 版本域 | 普通包 `DC 02`，首轮文件包 `0F 27` |
| `0x10–0x13` | tail | 上一包应答里的 4 字节，C 包必须原样带回 |
| `0x18` | 校验 | A 包为 0，C 包才有 |

所以「第一对能收到应答」是因为 `01`、`03` **恰好就是合法类型**；
从第三个包起类型变成 `05`，网关不认识 → 静默丢包 → 保活 B 整场失效。

这解释了诊断里全部细节：

- 每场开头 `保活 B 首包` 之后网关确实回了两包（诊断里没有对应的超时日志）；
- 第三包起 100% 超时，一路累计到 21、22 次；
- 会话在 ~10 分钟后被服务端释放（B 是会话续租，A 只是查流量）。

顺带纠正 1.3.3/1.4.1 的另一个误判：**272 字节的类型 7 报文不是 B 应答**，
它是网关对「文件包」的确认（长度域小端 `10 01` = 272、`0x02 = 0x10`，
与 `parse_keepalive2_response(..., file_packet=True)` 的判定完全一致）。
1.4.1 把它的 `0x10` 当 mirror 抄进后续请求，是第二层错误。

## 3. 这一版改了什么

1. **保活 B 按协议重写**（`[CONN]`）：
   - `0x05` 改成包类型：每轮先发 A 包（01）、收到应答后发 C 包（03）；
   - `0x01` 恢复成每包 +1 的计数器；
   - 每个会话第一轮先发一次「文件包」（版本域 `0F 27`），网关回 272 字节确认；
   - tail 只从 40 字节的 A/C 应答里取，272 字节确认的 `0x10` 不再使用；
   - A 包校验字为 0、C 包才带校验字（对齐抓包）。
2. **保活 B 的失败不再计入掉线判定**：会话存亡只看保活 A（带服务端统计）和在线巡检。
   以前 B 超时会把 `misses` 顶到阈值，日志里还会出现「保活A 超时（第 2 次）」这种误导。
3. **在线巡检不再「探针不通就重登」**：连续 4 次探不到外网时，如果保活 A 还在应答
   （60s 内），说明服务端会话还活着，只记日志不重登；保活真停了由 120s 检查负责重连。
4. 诊断日志改成逐包记录 `type / counter / tail`，下次一眼就能看出网关回的是哪一类。

## 4. 真机验证要点（下次跑 8h 看这三行）

```
保活B 发送 type=0x01 counter=0x05 … tail=0x…
保活B 应答 type=0x02 counter=0x…  tail=0x…
保活B 发送 type=0x03 counter=0x06 … tail=0x…   ← tail 必须等于上一行
```

判定标准：**不再出现「保活B 无应答（累计 N 次）」连成串**，
且 `状态：idle → discovering` 在 8 小时内不再周期性出现。
