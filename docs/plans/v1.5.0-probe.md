# 1.5.0 规划：让探针说出真相

## 0. 这一版要解决什么

一句话：**现在的探针会撒谎。**

它只测 `http://<host>/generate_204`（80 端口）。只要 80 端口返回 204，就判定
「在线」。但 2026-11-11 在真实校园网里测到一种状态：

| 探测 | 结果 |
|---|---|
| `http://connect.rom.miui.com/generate_204` | **204** ✅ |
| `https://www.baidu.com` | 200 ✅ |
| `https://net.jlu.edu.cn` | 200 ✅ |
| `https://github.com` | ❌ TLS 握手被切断 |
| `https://www.google.com` | ❌ TLS 握手被切断 |
| `https://1.1.1.1` | ❌ TLS 握手被切断 |

**80 端口全通，443 端口 TLS 全断。** 探针返回 204，App 显示"在线"，
但用户实际什么都打不开。这就是"显示已连接但没网"的一个真实成因。

## 1. 实测证据（2026-11-11，JLU.WIFI）

> **重要更正**：本文件初版把「境外 443 全部 `unexpected eof`」当成校园网的
> 封锁行为。后续用 `IP_BOUND_IF` 严格绑物理网卡复测，**结论反过来了**：
> 那些 `unexpected eof` 全部来自**经过代理 TUN** 的路径，不是校园网直连。
> 详见 §1.3。保留这段记录是为了说明「测量方法本身会影响结论」。

### 1.1 直连矩阵（`IP_BOUND_IF` 绑 en0，唯一能绕开代理 TUN 的方式）

| 目标 | 80 | 443 |
|---|---|---|
| github.com | 通 | **通** |
| github（第二台） | 通 | **通** |
| github-pages | 通 | **通** |
| fastly / reddit | 通 | **通** |
| opendns | 通 | ✗ |
| cloudflare-dns (1.1.1.1) | 通 | ✗ |
| google | ✗ | ✗ |
| twitter | ✗ | ✗ |
| facebook | ✗ | ✗ |
| google-dns / quad9 | ✗ | ✗ |
| baidu / qq | 通 | 通 |

字节级验证（直连 443 的真实返回）：
- GitHub 的 443 → `15 03 03 00 02 02 28`（TLS alert，说明 TLS 层通）
- 百度的 443 → `16 03 03 00 4a 02 ...`（ServerHello，握手正常）

### 1.2 由此得到的真实规律

**不是「443 端口被封锁」，而是按目标 IP 段选择性封锁。**

- GitHub 全家 + Fastly 段：80 和 443 全通
- Google / Twitter / Facebook / 公共 DNS 段：80 和 443 全超时

这解释了为什么机场节点几乎全挂：它们大多落在被封的段（Cloudflare、
Google Cloud、AWS）。但**不是端口封锁**——同一个 443 上，GitHub 就是通的。

### 1.3 测量方法的坑（必须记住）

`curl --interface en0` **只改源地址，仍然走 TUN 路由**，测出来的不是物理直连。
只有 `IP_BOUND_IF`（socket 选项）才真正绕开路由表。

同一时刻的对照：

| 路径 | github.com:443 |
|---|---|
| `IP_BOUND_IF` 直连 | `responded` ✅ |
| 经代理 TUN（openssl 默认） | `unexpected eof` ❌ |

**所以「境外 TLS 不通」这个现象是真的，但原因是代理路径，不是校园网。**
这正是探针必须走 `IP_BOUND_IF` 的原因（`PLAN.md:22` 早已写明）。

### 1.4 另一个真实缺陷：探针目标本身不可达

现有默认目标 `gstatic` / `cloudflare` / `connect.rom.miui.com` 在直连下
**全部不可达**（它们的兜底 IP 都在被封段）。
`connect.rom.miui.com` 只有解析到某个可用节点时才通。

这会让探针把「能上国内」误判成「完全没网」——与 §2 的「误报在线」是
一对相反的毛病：**探针两头都会撒谎**。

## 2. 探针现在错在哪

`ConnectivityProbe.run` 的判定（`Sources/JLUGateNet/ConnectivityProbe.swift`）：

```swift
switch head.statusCode {
case 204:              return .healthy          // ← 80 端口 204 就判定健康
case 200 / 3xx:        return .captivePortal
default:               失败，继续试下一个
}
```

三个具体缺陷：

1. **单端口**：只探 80，无法发现 443 的问题
2. **无 TLS 层**：`httpGet` 只发明文 `GET`，从不做 TLS 握手，所以测不到
   "TCP 通但 TLS 断"这种状态
3. **204 被当成"一切正常"**：`PLAN.md:107` 早就写明
   「`generate_204` 返回 204 只能证明"有网"，不能用于任何认证链路验证」，
   但代码里仍然把它当健康判据

## 3. 设计：分层探针

### 3.1 三层判定

| 层 | 探测 | 能证明什么 | 失败意味着 |
|---|---|---|---|
| L1 会话层 | `http://…/generate_204` | 有 IP、能到网关、会话可能还在 | 彻底断网 |
| L2 出口层 | `http://<literal-ip>:80` | 真能出网（80） | 出口被封 |
| L3 加密层 | `https://<host>:443` TLS 握手 | 能建立加密连接 | **TLS 被拦截** |

### 3.2 新增结论类型

现有 `ProbeOutcome` 只有 `healthy` / `captivePortal` / `unreachable`。
新增一个组合状态：

```swift
/// 能连上网关和 80 端口，但 443 的 TLS 握手过不去。
/// 典型成因：校园网/运营商在阻断出境 TLS（换代理节点也无效）。
case tlsBlocked(detail: String)
```

这个状态**必须**和 `unreachable` 区分开：前者是"有网但加密通道被断"，
后者是"根本没网"。给用户的建议完全不同。

### 3.3 探测顺序（成本从低到高）

```
1. L1：80 端口 generate_204
   ├─ 204        → 继续 L3（不能就此收工！）
   ├─ 200/3xx    → captivePortal（明确）
   └─ 失败       → 继续试下一个目标，全失败则 unreachable

2. L3：443 端口 TLS 握手（仅当 L1 成功时）
   ├─ 成功       → healthy（真健康）
   └─ 失败       → tlsBlocked
```

**为什么 L1 成功还要测 L3**：这次实测的正是这种情况。L1 通过而 L3 失败，
用户实际是"能上国内、不能上境外"，必须如实报告。

### 3.4 TLS 探测怎么实现

不能用 `URLSession`（`PLAN.md:22` 已禁止：无法绑定出口网卡，TUN 下会被劫持）。
也不引入新依赖。

最小实现：在 `ProbeTransport` 上新增一个方法，发一个**最小 TLS ClientHello**
然后看对端是否回 ServerHello 的第一个字节（`0x16` handshake）。

```swift
/// 只做 TCP 连接 + 发 ClientHello + 读第一个字节，判断 TLS 是否被放行。
/// 不校验证书、不完成握手——目的是区分"TLS 被切断"和"TLS 可用"。
func tlsHandshake(ip: IPv4Address, host: String, port: UInt16,
                  interface: InterfaceSnapshot, timeout: Duration) async throws -> TLSProbeResult
```

结果枚举：

```swift
public enum TLSProbeResult: Sendable, Equatable {
    /// 收到了 TLS 记录层响应（0x16 handshake 或 0x15 alert）
    case responded
    /// TCP 通了，但发完 ClientHello 对方直接断开（EOF）
    case closedAfterHello
    /// TCP 都没连上
    case unreachable
}
```

**`closedAfterHello` 就是这次实测到的 `unexpected eof`**，它是判定
`tlsBlocked` 的直接依据。

### 3.5 不做什么

- **不引入 OpenSSL / 第三方 TLS 库**：只要判断"有没有响应"，手写 ClientHello 足够
- **不改 `DrcomEngine` / `BSDChannel`**：它们在冻结区，且与本次无关
- **不改认证链路**：这是纯探测层改动，不碰登录/保活
- **不做完整 TLS 握手**：不需要证书校验，只要第一个字节

## 5. 验收标准

- [ ] 单测覆盖：L1 通 + L3 通 → `healthy`
- [ ] 单测覆盖：L1 通 + L3 断（`closedAfterHello`）→ `tlsBlocked`
- [ ] 单测覆盖：L1 挂 → `unreachable`（不回退成 `tlsBlocked`）
- [ ] 单测覆盖：`tlsBlocked` 不会被当成 `healthy`（这是本版的核心回归）
- [ ] 真机验证：在 2026-11-11 那个环境下，App 显示"加密通道被拦截"而不是"在线"
- [ ] `make ci` 通过（含连接冻结守卫）

## 6. 给用户的提示文案（要点）

`tlsBlocked` 出现时，要明确告诉用户：

1. **不是你的问题**，是网络在拦加密流量
2. **换节点没用**——因为拦截按端口，不按节点
3. **能做什么**：换非 443 端口的节点 / 用 WebSocket+CDN 伪装 / 等网络恢复

这条文案很重要：它直接避免用户像 2026-11-11 那样，把所有节点换一遍却毫无效果。
