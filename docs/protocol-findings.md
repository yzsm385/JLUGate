## 2. Challenge（20 字节）

```
00  01 03 1d 63 31 00 00 00 00 00 00 00 00 00 00
10  00 00 00 00
```

| 偏移 | 值 | 说明 |
|---|---|---|
| 0x00 | `0x01` | 类型：Challenge |
| 0x01 | `0x03` | 子类型（后续两次分别为 `0x04`、`0x05`） |
| 0x02–0x03 | `0x1d63` | **序号**（下一次 `0x2f63`，再下一次 `0x3f63`） |
| 0x04 | `0x31` | 常量（可能是版本位） |
| 0x05–0x13 | 全 0 | 保留 |

## 3. Challenge 应答（76 字节）

```
0000  02 03 1d 63 14 cb 72 0f 01 00 01 00 f3 03 e8 f0
0010  00 00 00 00 31 8c 3b 6f f0 00 a8 ac 00 00 4f e4
0020  16 c1 00 00 00 00 dc 02 00 00 00 ×(76-40)
```

- `0x00–0x01`：`02 03` 回显类型/子类型
- `0x02–0x03`：`1d 63` **回显序号**
- `0x04–0x07`：`14 cb 72 0f` — 4 字节（疑似时间戳/随机，**待验证**）
- `0x14–0x17`：`31 8c 3b 6f` = 客户端 IP `192.0.2.10`（**已确认**）
- `0x18–0x1b`：`f0 00 a8 ac` — 疑似端口与会话位
- 其余多为 0，长度固定 76。

> 注意：**没有在应答里直接看到"4 字节 salt"**。可能的 salt 是 `0x04–0x07` 那 4 字节（`14 cb 72 0f`），需结合登录包的 MD5 反推验证（见 §7）。

0020  00 ×(80-0x1f)

### 5.1 摘要 A 的算法（已实测验证 ✅）

```
salt = Challenge 应答(0x02) 的字节 0x04..0x07
digestA = MD5( 0x03 ‖ 0x01 ‖ salt ‖ password_utf8 )
```

验证：账号 `20230001`、密码 `test-pass-2024`、salt `49cb720f` →
`MD5(0301 49cb720f 61686176363834363834)` = `d030ec3cfa269619e0d3c3224b3e9aa6`，
与 20:29:37 那次登录包 `0x004` 处的 16 字节**逐字节一致**。

> 注意：salt 必须取**紧邻本次登录的那次** Challenge 应答。本次抓包里 `0x04..0x07` 依次为
> `14cb720f` / `49cb720f` / `6ecb720f`，用错一个就永远算不对（我第一轮就是踩了这个坑）。

**关键结论**：登录包不是 128/334，而是**固定 342 字节**；MAC 在 **0x14C**，账号在 **0x14**（32 字节定长），版本串在 **0xC0**，主机名在 **0x6E**。这三处是"必须逐字节照抄"的地方。

## 6. 登录结果

**失败（37 字节）**：

```
05 00 00 05 15 00 …(至 0x18)… "ldap.auth error" 00 00
```

- `0x00 = 0x05` → 失败类型
- 原因串从 **0x18** 开始，NUL 结尾：`ldap.auth error`
- **这就是"密码错误"的实测表现**（U4 部分结案）；服务端把原因明文回给我们，可以直接展示。

**成功（45 字节）**：

```
04 00 00 05 00 d9 04 00 00 b2 f8 09 00 ff ff ff ff ff
00 00 00 00 00 "Drco" 0a 64 3d 03 e6 87 31 8c 3b 6f
01 45 b0 05 00 03 01 00
```

- `0x00 = 0x04` → 成功
- 0x18 起是 `Drco` + 服务器 IP `10.100.61.3` + 客户端 IP `192.0.2.10`
- 中间 `d9 04 00 00 b2 f8 09 00` 等疑似计费/流量参数（**待验证**，可能含"可用时长/流量"）

## 7. 保活（两种，都是"请求-应答"）

### A 型：38 → 72

请求（38）：

```
ff d4 c7 41 ff 59 42 0c 9f 95 65 dd 35 c7 ee ea
c1 00 00 00 44 72 63 6f 0a 64 3d 03 94 87 31 8c
3b 6f 01 f4 1d 63
```

- `0x00 = 0xFF`：注意**不是 0x07**
- `0x00–0x0F`：16 字节（疑似摘要，**每次相同**——同一会话内固定）
- `0x10–0x13`：`c1 00 00 00`
- `0x14`：`Drco` 魔数 + `0x18` 服务器 IP + `0x1C` 客户端 IP
- `0x20–0x21`：`01 f4`
- `0x24–0x25`：`1d 63` — **与 Challenge 的序号一致**（会话标识）

应答（72）：

```
07 01 10 00 06 00 1d 63 00 45 f8 4c 31 8c 3b 6f
a8 ac 00 00 4f e4 16 c1 00 00 00 00 dc 02 00 00
26 00 00 00 09 00 00 00 00 00 00 00 d8 04 00 00
a9 f8 09 00 ff ff ff ff ff ff ff ff ff ff ff ff
00 ×8
```

- `0x00–0x03`：`07 01 10 00`（类型 7，子类型 1，**`0x0010` 疑似长度域**）
- `0x04–0x07`：`06 00 1d 63`（回显会话号 `1d63`）
- `0x08–0x0B`：`00 45 f8 4c`
- `0x10–0x1F`：含客户端 IP、`4f e4 16 c1`
- `0x20` 起：`dc 02 00 00`、`26 00 00 00`、`09 00 00 00`、`d8 04 00 00`、`a9 f8 09 00` —— **流量/时长统计**（随时间递增，可用来做"本次会话用量"显示）

### B 型：40 → 40

请求：

```
07 05 28 00 0b 01 dc 02 e4 b8 73 00 00 00 00 00
7a 44 f8 4c 00 ×20
```

应答：

```
07 05 28 00 0b 02 dc 02 e4 b8 73 00 00 00 00 00
72 46 f8 4c 00 ×20
```

- `0x00`：`0x07`
- `0x01`：子类型，**请求 `05`、应答 `05`**（也有 `06`）
- `0x02–0x03`：`28 00` = 40，**长度域**
- `0x04`：`0b` 常量
- `0x05`：**序号**，请求/应答**共用同一个自增计数**（`01→02→03→04…`，观察到一个会话内到 0x10）
- `0x06–0x07`：`dc 02` = 732（疑似会话/端口号，与 challenge 包里的 `dc02` 一致）
- `0x08–0x0B`：`e4 b8 73 00` — 时间戳
- `0x14–0x17`：请求 `7a44f84c`、应答 `7246f84c` — 每次不同（**校验/时钟**，待验证）

> 实测节奏：A/B 两种交替，约每 10s 一轮；A 型一轮内连发两对 40/40 的情况也观察到（20:29:54 连续 4 个 40 字节包）。

## 8. 仍然未知（下一轮抓包要补）

| 编号 | 问题 | 为什么重要 |
|---|---|---|
| P1 | ~~摘要 A / B 的算法~~ | **✅ A 已破**（§5.1）。B 疑似随机 nonce，先填随机 16 字节，用真机验证服务端是否校验 |
| P2 | 40 位十六进制串（0x0F6）是什么：`SHA1(?)` 还是服务端下发令牌 | 若是随机令牌就没法自造 |
| P3 | 0x136 附近的 16 字节（疑似第三个摘要） | 同上 |
| P4 | 登录成功后 `0x04` 包里的统计字段含义 | 可用于显示流量 |
| P5 | 服务器是否会**主动**发保活探测（本次 60s 静置未见） | 决定是否要被动应答逻辑 |
| P6 | 源端口 61440 是否被强制（本次全程 61440，未做对照） | 决定端口绑定是否必须 |

> 补 P1 的最快方式：**不需要第二台设备、不需要同时在线**。在同一台机器上"退出 → 重新登录"即可，属于先后发生。
>
> 本次抓包其实已经包含两次登录（序号 `1d63` 与 `3f63`，摘要 A 分别是 `d030ec3c…` 与 `f112b888…`，且 challenge 应答的 `0x04–0x07` 从 `14cb720f` 变成 `6ecb720f`）——**足以证明摘要与 challenge 相关**。
>
> 仍缺的是：**其中任意一次登录所用的密码**。只要知道密码，就能验证 `MD5(type‖subtype‖salt‖password)` 是否成立。
> 推荐做法：用**假密码**登录一次（服务器会返回 `ldap.auth error`，但登录包已经发出），抓包后把那个假密码告诉我；不必提供真实密码。

## 9. 对实现的影响（已同步到 PLAN.md）

1. 帧识别改为 `(type, subtype, length)` 三元组，长度表用本文 §1。
2. `parseSalt` 作废——salt 位置未确认，登录包摘要算法待 P1。
3. 保活必须实现**两种**（38/72 与 40/40），且 B 型的序号是**请求与应答共用**的自增计数。
4. 登录失败要**直接展示服务器给的原因串**（`ldap.auth error`），不要自己翻译成"密码错误"——将来出现"欠费""顶号"时同理。
5. 登录包里的 MAC/账号/版本/主机名必须按 §5 的偏移逐字节填，不能自创。

### 10.3 返回

```json
dr1003({"result":0,"wopt":0,"msg":1,"uid":"...","ss4":"...","msga":"userid error1"})
```

- `result == 1` 或 `"ok"`：成功（仍需 204 探针确认）。
- `result == 0`：失败。`msg` 是**数字代码**，`msga` 是服务端原因串：
  - `0/1` + `userid error1` / `ldap auth error` → 账号或密码不对；
  - `2` → 账号/终端已在线；
  - `3` → IP 不在允许范围；`4` → 余额/时长不足；`5` → 停机；
  - `6` → 系统繁忙；`7` → 超出时长/流量。
- 响应头是 `charset=gbk`，要按 GB18030 解，否则中文原因会乱码。

### 10.4 还有一个坑：凭据"已验证"状态

网页认证没有 Dr.Com 的会话号，以前不会触发 `AuthTelemetry.session`，保存的密码
永远停在"未验证"，下次启动又被向导拦下。1.4.1 起在 **204 确认在线后**发
`portalAuthenticated(account:)`，App 据此 `CredentialStore.markVerified`。
