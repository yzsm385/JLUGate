# JLU Gate 1.5.0

> 这一版做一件事：**让「有没有网」这个判断不再撒谎**。
>
> 1.4.x 里探针会在两个方向都说错话——明明有网却报断网，明明打不开却报已连接。
> 这一版把判定改成多层、多目标，并且把「链路通、但加密通道被切断」单独拎出来说清楚。

## 原来的问题

### 问题一：80 端口通就报「已连接」

旧探针只看 `generate_204` 有没有返回 204。只要 80 通，界面就亮绿灯。
可 80 通不代表能上网——443 的加密连接被切断时，用户看到「已连接」却什么都打不开。

### 问题二：DNS 解析到不可达 IP 就报「没网」

这个更隐蔽。同一个域名，不同 DNS 服务器会给出**完全不同**的地址：

| DNS | 解析结果 | 可达性 |
|---|---|---|
| 公共 DNS | 境外地址 | 在校园网里不可达 |
| 校内 DNS | 国内 CDN 节点 | HTTP 204 正常 |

旧代码只取**第一个**成功的解析结果。如果先问到公共 DNS，拿到一个不可达的
地址，就直接判整条链路不通。实测同一台机器、同一时刻：

- `jlugate-probe --portal-check` → 「在线判定失败」
- `jlugate-probe --portal-check --dns <校内DNS>` → 「已在线」

**同一个网络，结论完全相反。** 这不是网络问题，是探针取样方式的问题。

## 这一版怎么改的

### 1. 加了一层加密通道判定

除了 80 端口的 204，再连一次 443、发一个最小 TLS ClientHello，看对端有没有
回 TLS 记录层字节。三种结论：

| 结论 | 含义 |
|---|---|
| `responded` | TLS 层通 |
| `closedAfterHello` | TCP 通、发完 Hello 就被切断 |
| `unreachable` | 连不上 |

判定用**多个目标**（GitHub + 百度），必须**全部**呈现「TCP 通、发完 Hello 就 EOF」
才判「加密通道被切断」。单个目标失败只说明那个地址被拦，不能说明整条链路有问题。

新增结论类型 `tlsBlocked`，和「彻底没网」严格分开——因为给用户的建议完全不同。

### 2. DNS 多结果降级

改成收集**所有** DNS 服务器的解析结果，去重后依次尝试；DNS 解析成功后仍把
内置兜底地址排在后面作为最后手段。每个目标最多试 3 个地址（逐个试会把探针
拖到 46 秒，而探针每 30 秒就要跑一轮）。

默认 DNS 顺序也改成**校内优先**：`10.10.10.10` / `10.10.10.11` → 阿里
`223.5.5.5` → `1.1.1.1`。实测 `8.8.8.8` 在校园网直连下完全不通，
`1.1.1.1` 虽然能应答但会解析到境外不可达地址。

### 3. 状态机新增「加密通道被切断」

这是一个独立状态，有自己的颜色、图标和文案。**关键是建议不同**：

> 换代理节点没用！拦截按目标地址生效，换哪个节点都一样。

这句话直接省掉一轮无效排查。以前遇到这种情况，用户（包括我自己）会把所有
节点换一遍，然后发现毫无效果——因为问题根本不在节点。

## 实测数据

2026-11-11/12，JLU.WIFI，用 `IP_BOUND_IF` 绑定物理网卡（这是唯一能绕开代理
TUN 的方式），每个目标采样 6 次：

| 目标 | 443 | 稳定性 |
|---|---|---|
| github.com | 通 | 6/6 |
| github-pages | 通 | 6/6 |
| fastly | 通 | 6/6 |
| baidu | 通 | 6/6 |
| qq | 通 | 6/6 |
| cloudflare-dns | 不通 | 0/6 |

**稳定通或稳定不通，不是抖动。** 由此得到的结论是：这个网络按**目标地址段**
选择性拦截，不是按端口拦截。同一时刻经代理访问境外则全部失败。

完整研究记录见 `docs/network-probing-research.md`。

## 一个方法教训（值得单独写出来）

排查过程中，本机路由表被代理改成了「路由分裂」：

```
1 → utun4    2/7 → utun4    4/6 → utun4    8/5 → utun4
```

这四条规则加起来覆盖整个 IPv4 空间，比 `default` 更精确。所以：

- `curl --interface en0` 只改**源地址**，路由查找仍按目的地址 → **仍走 TUN**
- `nc -s <本机IP>` 同理 → **仍走 TUN**
- `IP_BOUND_IF`（socket 选项）才是内核级绑定 → **真绕开**

我最初用前两种方法测，得出的「境外全部不通」结论是错的——测的其实是代理路径。
这个错误直接导致了两个错误的判断（「校园网封锁所有出境 TLS」、「443 端口封锁」），
都在这一版里更正了。

## 验证

- JLUGateNet 118 测试（新增 11 个）、JLUGateCore 243 测试（新增 3 个），全过
- 核心回归：80 返回 204 但 TLS 被切断 → 必须判 `tlsBlocked`，不能 `healthy`
- 反向回归：80 就不通 → `unreachable`，不能误报 `tlsBlocked`
- DNS 回归：第一个 DNS 解析到不可达 IP 时，仍能用第二个 DNS 的结果探通
- 真机：正常网络下探针报 `healthy`，不再误报断网
- `make ci` 通过（隐私扫描 + 连接冻结守卫）

## 已知限制

**探针能准确告诉你「校园网这条链路通不通」，但无法解释「为什么代理境外不通」。**
代理节点侧的连接是加密的，App 看不到，只能看到它有没有建立境外连接。

如果你的情况是「国内正常、境外全挂」，先看代理软件自己的日志，而不是怀疑校园网。

## 升级建议

- 从 1.4.x 升级：直接覆盖安装即可，配置和账号密码保留
- 这一版不涉及认证链路改动（`AuthCoordinator` 只加了一个 case 分支，
  不改既有逻辑），1.4.11 修的问题不受影响
